## 0. Verdict en une page

**La bonne nouvelle d'abord** : le cœur de l'isolation multi-tenant est **solide et prouvé**. Chaque table métier a la RLS `ENABLE` **et** `FORCE`, les 4 portes (lire/créer/modifier/supprimer) sont policées avec des prédicats symétriques, l'`espace_id` est gelé par un *trigger* qui bat même le `service_role`, les fonctions à passe-droit ont leur `search_path` gelé, et il n'y a **aucune vue exposée** ni **aucun accès `anon`** dans le schéma public. Côté auth : **aucune clé `service_role` côté client**, hook d'inscription durci et fail-closed, purge de session au logout. Côté worker : tokens haute entropie, OTP solide une fois activé, pas de `service_role` dans le worker, pas de SSRF/open-redirect. **Aucun secret réel n'a fuité dans l'historique git.** Je n'ai trouvé **aucun trou d'isolation cross-compte prouvable** par la lecture du code.

**Le problème** : ce n'est pas l'isolation qui va faire mal, ce sont **deux familles de failles P0** qui touchent directement la valeur commerciale et juridique du produit :

# PARTIE I — Le modèle de sécurité de Propryo, expliqué simplement

> Cette partie explique **comment Propryo protège les comptes et les données**, en langage clair, avant la liste des failles. Objectif : comprendre *où sont les murs* et *pourquoi un mur qui a l'air solide peut ne pas l'être*.

## 1. L'idée de base : chaque client vit dans sa « bulle » (espace)

Propryo est **multi-tenant** : un seul logiciel, une seule base de données, beaucoup de clients dedans. Pour que le client A ne voie jamais les données du client B, chaque donnée (bien, bail, mouvement, document…) porte une étiquette : **`espace_id`** — l'identifiant de la bulle à laquelle elle appartient. Tu es rattaché à un ou plusieurs espaces via une table d'appartenance (`espace_members`).

La règle d'or : **tu ne peux lire/écrire que les lignes dont l'`espace_id` correspond à un espace dont tu es membre.**

## 2. Qui fait respecter la règle ? Le serveur, jamais le navigateur

C'est le point le plus important, et le plus contre-intuitif.

Le code qui tourne dans le navigateur (le gros `index.html`, les modules `js/`) **n'est pas une barrière de sécurité**. Pourquoi ? Parce que n'importe qui peut ouvrir les outils de développement, modifier le JavaScript, ou carrément ignorer l'application et parler **directement** à la base. Supabase expose automatiquement une **API REST** : chaque table du schéma `public` est accessible par une URL, avec la clé publique (`anon key`) qui est, par définition, dans le navigateur de tout le monde.

Donc : **si la seule protection d'une donnée est « le bouton n'est pas affiché » ou « le front ne l'envoie pas », elle n'est pas protégée.** Un attaquant n'utilise pas tes boutons.

La vraie barrière, c'est **la RLS (Row-Level Security) de PostgreSQL** : des règles écrites *dans la base*, que le serveur applique à CHAQUE requête, quel que soit l'outil. C'est le videur à l'entrée : peu importe comment tu arrives (l'appli, un script, curl), il vérifie ton bracelet `espace_id` avant de te laisser voir ou toucher une ligne.

**Conséquence pour cet audit :** je ne regarde jamais « est-ce que le front empêche X ». Je regarde « est-ce que la *base* empêche X, même si le front est contourné ». Une protection seulement front = une faille. (Et c'est précisément le cas de **P0-2** : le front échappe mal les données.)

## 3. Les deux interrupteurs de la RLS : `ENABLE` **et** `FORCE`

Activer la RLS se fait en deux temps, et **oublier le second est un piège classique** :

- `ENABLE ROW LEVEL SECURITY` : allume les règles… mais **le propriétaire de la table (et les fonctions « SECURITY DEFINER ») continuent de tout voir**, RLS ignorée.
- `FORCE ROW LEVEL SECURITY` : force les règles **même pour le propriétaire**.

Une table avec `ENABLE` mais sans `FORCE` peut sembler protégée et ne pas l'être selon qui interroge. *Bonne nouvelle : Propryo applique les deux sur toutes les tables métier (vérifié).* Deux tables d'infrastructure (`beta_allowlist`, `app_admins`) n'ont que `ENABLE` — sans impact client, détaillé plus bas.

## 4. Les « policies » : 4 portes par table (lire / créer / modifier / supprimer)

Pour chaque table, la RLS se décline en règles distinctes pour **SELECT / INSERT / UPDATE / DELETE**. Deux pièges récurrents :

- **Une porte oubliée** : une règle pour lire mais aucune pour modifier → l'opération est soit refusée (sûr) soit grande ouverte (dangereux).
- **`USING` vs `WITH CHECK`** : `USING` = « quelles lignes tu as le droit de voir/toucher » ; `WITH CHECK` = « à quoi la ligne a le droit de ressembler *après* ton écriture ». Oublier le `WITH CHECK` permet parfois de **déplacer une ligne chez le voisin** (changer son `espace_id`). *Vérifié : Propryo met les deux, avec le même prédicat. Ce piège est évité.*

## 5. Les fonctions « SECURITY DEFINER » : des passe-droits à surveiller

Certaines opérations (créer un espace, purger un espace, poser un verrou d'immuabilité) passent par des **fonctions serveur** `SECURITY DEFINER` : elles s'exécutent au-dessus de la RLS. C'est nécessaire, mais chaque fonction est un petit passe-droit. Deux vérifications vitales, **toutes deux OK chez Propryo** :

1. **`search_path` gelé** (`SET search_path = ''`) → neutralise le détournement de fonction/table leurre.
2. **Validation des arguments** → ex. `purge_mon_espace` vérifie que *tu es propriétaire de cet espace* avant d'agir, sinon un attaquant purgerait l'espace du voisin.

## 6. Storage, Realtime, et l'API auto ne sont pas « gratuits »

- **Storage** (PDF de baux, photos d'EDL) a **ses propres règles**. *Vérifié : le bucket est privé et les règles scopent par espace **et** par entité (SCI) depuis la migration `0031`.*
- **Realtime** (mises à jour en direct) doit être **filtré par espace/SCI**. *C'est ici que se trouve le trou latent RT-1 : le filtre est au niveau espace, pas SCI.*
- **L'API REST auto** : toute table **ou vue** du schéma `public` est exposée. *Vérifié : aucune vue, aucune table sans RLS, aucun accès `anon`.*

## 7. Les documents signés : au-delà de l'isolation, l'intégrité

Un bail/EDL **signé** a une valeur **juridique**. La question n'est plus seulement « qui peut le voir » mais :

- **Immuabilité** : après signature, peut-on le *modifier/supprimer* ? *Vérifié : un trigger bloque UPDATE/DELETE sur une ligne verrouillée — solide.*
- **Intégrité** : le contenu signé est-il scellé par une empreinte (hash) liée au document présenté ? *C'est ici que **P0-1** casse tout : le relais scelle le PDF que le signataire renvoie, sans le comparer à l'original.*
- **Non-répudiation** : la preuve lie-t-elle *le bon document* + *la bonne personne* + *l'horodatage* + *l'OTP* ?
- **OTP** (code 6 chiffres) : entropie, expiration, **limite d'essais**. *Vérifié : la primitive OTP est bien faite — mais désactivée par défaut aujourd'hui.*

## 8. Le poste partagé : un angle mort du « hors-ligne »

Propryo est une **PWA** : pour marcher hors-ligne, elle garde des données sur la machine (localStorage, IndexedDB, cache du service worker). Sur un **ordinateur partagé**, la question : quand A se déconnecte et B se connecte, **tout ce qui appartient à A est-il effacé** ? *Réponse nuancée : le cache du service worker ne contient pas de données utilisateur (bon), mais les photos d'EDL non encore uploadées restent dans IndexedDB (F14.1), et si A ferme l'onglet sans se déconnecter, B est auto-connecté en tant que A (F14.2).*

## 9. Ce que la lecture du code NE permet PAS de trancher

Un audit boîte blanche a des angles morts. Certaines choses ne se voient pas dans les fichiers et **doivent être testées sur la vraie base / le vrai hébergement** :

- Droits par défaut accordés aux rôles `anon`/`authenticated` au niveau Postgres.
- Si une migration a **réellement été appliquée** en prod.
- Les **réglages du dashboard Supabase** (anti-brute-force, hook d'inscription, templates d'email, allowlist de redirection).
- Les **en-têtes HTTP réels** servis par GitHub Pages / Cloudflare.
- Si un **secret est encore valide** (ex. la clé relais à régénérer).

Ces points sont regroupés dans la **checklist de test réel** en fin de rapport.

## A · Intégrité & non-répudiation des documents SIGNÉS (surface 11)

### 🔴 P0-1 — Le PDF « signé » n'est jamais lié à l'original : un signataire substitue un document arbitraire
**Prouvé par raisonnement.** Ancrages : `relay/src/index.js:246-260`, `relay/src/sessions.js:134,146-147`, `relay/public/sign/proof.js:19-33`, `index.html:8375-8377,8418-8421`.

À l'upload, l'endpoint `POST /api/sessions/:id/signed` ne valide **que** les *magic bytes* `%PDF` et la taille (≤ 20 Mo), puis stocke les octets tels quels et scelle la session :

```js
// relay/src/index.js:246-260
const bytes = new Uint8Array(await c.req.arrayBuffer());
const v = validatePdfUpload(bytes, contentType);   // seulement %PDF + ≤20MB
...
const session = await recordSignature(c.env, sessionId, { signedBytes: bytes, proof, clientProof });
```

`recordSignature` hashe **les octets uploadés** (pas l'original) et **écrase l'original** avec :

```js
// relay/src/sessions.js:134,146-147
pdfSha256: await sha256hex(signedBytes),       // hash du doc fourni par l'attaquant
await putSignedPdf(env, sessionId, signedBytes);
await putOriginalPdf(env, sessionId, signedBytes);   // l'original est détruit
```

Il n'y a **aucune comparaison serveur** entre le PDF original (stocké à la création, `sessions.js:34`) et les octets « signés ». La preuve client (`X-Sign-Proof`) ne porte **aucun hash de document** — uniquement `{sigId, signerName, role, signedAt, consent, luApprouve, openedAt, readCompletedAt}` (`proof.js:19-33`). Côté app, l'ingestion hashe aveuglément **ce que le relais retourne** et le scelle `locked:true` (`index.html:8418-8421`), sans jamais le comparer au PDF envoyé. Et `bail-content-hash.js` calcule une empreinte depuis les **termes locaux**, pas depuis le PDF → il ne détecte pas non plus la substitution du PDF.

**Scénario d'attaque.** Le signataire (ou quiconque détient le lien `/s/:sessionId`, cf. P0-5) ouvre la page de signature, obtient un `X-Sign-Token` valide (minté dans `window.__SIGN_TOKEN__`, `sign-page.js:43`), et au lieu du PDF original tamponné, **POST un PDF totalement différent** (autre loyer, autres clauses, page blanche). Le relais l'accepte, le stocke comme résultat signé, enregistre `pdfSha256` de la forgerie, marque la session `completed`. L'app du bailleur télécharge la forgerie, la hashe, la scelle comme « bail signé ». Plus tard le signataire répudie (« ce n'est pas le document que j'ai signé ») — **et la preuve serveur lui donne raison**, puisque `pdfSha256` décrit la forgerie.

**Impact :** la valeur juridique de la signature électronique est détruite. C'est le **bloqueur de release** de tout le produit « signature à distance ».

**Piste de correction (non appliquée) :** lier la signature à l'original — soit refuser un upload `/signed` dont le hash texte/structurel du contenu (hors annotations de signature) diffère de l'original stocké ; soit, plus robuste, **tamponner côté serveur** à partir de l'original stocké + l'image de signature, de sorte que le signataire ne fournisse jamais les octets du document ; et embarquer le hash de l'original dans `X-Sign-Proof`, vérifié serveur.

### 🔵 P0-1-bis — Falsification d'un doc « signé » par INSERT direct (le verrou est UPDATE/DELETE-only)
**Prouvé par raisonnement.** Ancrages : `0014:6-7` (INSERT jamais intercepté), `0015:24-26`, `js/core/store-mapping.js:131,59`.

Le trigger d'immuabilité `prevent_locked_mutation` ne se déclenche que sur UPDATE/DELETE. À l'**INSERT**, un membre-rédacteur contrôle les colonnes de signature (le mapper les copie du client : `const locked = !!sg.locked && src != null && (src !== 'immotrack' || hash != null)`, `store-mapping.js:131`). Il peut donc **INSÉRER une ligne `baux`/`edl` neuve** pré-réglée `locked=true, signed_at=<date>, signature_source='externe', signatures=<jsonb forgé>` ; la contrainte `baux_immotrack_hash_chk` (`0015:24-26`) n'exige un `content_hash` que si la source est `'immotrack'` → `'externe'` n'en a pas besoin. La ligne devient ensuite immuable.

**Scénario :** un **gestionnaire délégué** dans un espace multi-utilisateurs fabrique, contre les données du propriétaire, un bail/EDL qui s'affiche comme « signé en externe » que le propriétaire n'a jamais signé, et qui ne peut plus être édité via l'app. Ce n'est pas une rupture d'isolation (ça reste dans l'espace/SCI accordé) ; c'est un problème d'intégrité/confiance **intra-espace** pour la gestion déléguée. Gravité 🔵 aujourd'hui (pas de gestionnaire délégué scopé en prod), à revoir **en même temps que P0-1** et avant d'ouvrir la gestion déléguée.

### 🟠 P0-5 — « Lien non transférable » non garanti : signer n'exige aujourd'hui ni OTP ni correspondance email
**Prouvé par raisonnement** (config actuelle) · **à confirmer en test réel** (valeurs déployées). Ancrages : `relay/src/index.js:156-163,177-201,241-244`, `relay/wrangler.toml:30`, `relay/public/sign.js:54`.

Le seul verrou dur sur `/signed` est le sign-token, **minté à quiconque ouvre le lien** (`GET /s/:sessionId`, pas de contrôle d'identité). L'OTP est derrière un flag **désactivé par défaut** (`wrangler.toml:30` `OTP_REQUIRED="false"`), et `verify-email` n'est **pas une précondition** de `/signed` (piloté par le client, donc contournable en appel direct). En configuration actuelle, l'**URL `/s/:sessionId` est l'unique justificatif** : transférée (règle d'auto-transfert email, écran partagé, lien épié), elle permet à un tiers de compléter la signature à la place du signataire. Le texte UX « lien non transférable » (`sign.js:54`) n'est pas encore appuyé côté serveur.

*La primitive OTP elle-même est saine une fois activée* : 6 chiffres CSPRNG avec rejection sampling (`otp.js:10-17`), TTL 10 min + verrou à 5 essais (`otp.js:6-7,31-33`), comparaison en temps constant (`otp.js:25-28`), hash lié à la session `sha256(sessionId:code)` (`otp.js:20-22`), usage unique (`sessions.js:90`). → **Activer `OTP_REQUIRED=true` + `EMAIL_MODE=resend` est le pré-requis prod** (cohérent avec la mémoire : pas de signature à distance avant OTP en prod).

### 🟠 P0-6 — Un token owner fuité détruit la preuve signée (pas de révocation)
**Prouvé par raisonnement.** Ancrages : `relay/src/index.js:310-311,347-353`, `storage.js:1`.

Les tokens owner sont des HMAC *stateless* **non révocables** (documenté, `index.js:310-311`). Un détenteur d'un `X-Owner-Token` fuité peut `DELETE /api/sessions/:id` (efface le PDF signé + la preuve) ou `GET …/result` (exfiltre le bail = PII). Seule mitigation : le TTL de 14 jours (`storage.js:1`) et le fait que le token ne circule jamais en URL. `reclaim` re-minte sans invalider le token fuité. Trade-off documenté — à garder au registre des risques.

### 🔵 PUB-1 — `beta_allowlist` et `app_admins` sans `FORCE`
**Prouvé par raisonnement.** Ancrage : `0038:30-31`.

Ces deux tables n'ont que `enable`, pas `force`. **Impact client : nul** — `FORCE` ne change le comportement que pour le *rôle propriétaire de la table*, jamais pour `anon`/`authenticated` (toujours soumis à la RLS dès qu'elle est `enable`). `app_admins` n'a qu'une policy self-read (écritures refusées aux clients), `beta_allowlist` est `is_app_admin`-only. C'est un **écart de cohérence / défense en profondeur** : ajouter `force` pour l'uniformité.

### 🔵 PUB-2 — `is_app_admin()` pas `revoke`-é de `PUBLIC` → `anon` peut l'appeler (retourne `false`). Négligeable (`0038:23-27`).

Postgres accorde `EXECUTE` à `PUBLIC` **par défaut** à la création d'une fonction. Les migrations font les `revoke` — mais il faut confirmer en prod qu'ils ont pris : avec la **clé anon**, `select *` sur chaque table et `rpc()` sur chaque fonction `SECURITY DEFINER` → tout doit renvoyer *permission denied* / vide.

## D · PWA / service worker sur poste partagé (surface 14)

**Bonne nouvelle :** le service worker **ne met pas en cache les réponses d'API authentifiées** — `sw.js:58` sort sur toute requête *cross-origin* (`url.origin !== location.origin → return`), et Supabase/relais sont cross-origin. Le Cache Storage ne contient donc que des **assets statiques same-origin** (identiques pour tous les users). **Pas d'empoisonnement de cache cross-user.**

### 🟠 F14.1 — Les photos d'EDL non-uploadées de A survivent dans IndexedDB jusqu'à (et pendant) la session de B
**Prouvé par raisonnement.** Ancrages : `js/app/supabase-entry.js:247,258-265,1210-1216`, `js/core/cache-purge.js:23-26,56-78`.

Le mécanisme, étape par étape :
1. Au **logout**, `_teardownSession` retire le miroir localStorage + le tag + le token auth (`supabase-entry.js:247,251,253`), mais **conserve volontairement** IndexedDB `immotrack_photos` quand il existe des binaires « idb-only » (photos sans copie Supabase Storage) — `:258-265` via `listIdbOnlyBinaries`. C'est **délibéré** (préserver une preuve légale : « des documents vivants n'existent QUE là »).
2. Le logout **supprime aussi `MIRROR_TAG_KEY`** (`:247`).
3. Au **login de B**, la décision de purge lit ce tag : `classifyMirrorTag(localStorage.getItem(MIRROR_TAG_KEY), user.id, …)` (`:1210`). Le tag a disparu → `classifyMirrorTag` renvoie **`'untagged'`** (`cache-purge.js:26`), **jamais `'other-user'`**.
4. Or IndexedDB n'est effacé **que** sur le verdict `'other-user'` : `if (cls === 'other-user') await _deletePhotosDb()` (`:1216`). Le verdict `'untagged'` épargne IndexedDB par conception.

**Résultat :** les photos d'EDL non-uploadées de A (intérieurs de logement, PII locataire possible) **restent physiquement dans IndexedDB** sur la machine partagée, à travers la session de B, **indéfiniment**. Elles ne s'affichent pas dans l'UI de B, mais **n'importe qui avec les DevTools** (Application → IndexedDB → `immotrack_photos`) peut les ouvrir. Le verdict de sécurité `'other-user'` est **structurellement inatteignable** après l'effacement du tag au logout.

## 2 · Isolation RLS table par table (surface 2)

### ✅ Isolation espace : solide et prouvée
**Prouvé par raisonnement.** (détails des ancrages dans les tableaux de la Partie C ci-dessus et ci-dessous)

- **`ENABLE` + `FORCE`** sur toutes les tables métier (cf. tableau surface C).
- **4 commandes policées** partout ; les **UPDATE portent `USING` + `WITH CHECK` avec le même prédicat** (`0010:100-101`, `0030:190-193`) → pas d'asymétrie « lire puis déplacer chez le voisin ». Les **INSERT** ont un `WITH CHECK` = prédicat d'écriture sur l'`espace_id`/entité propre.
- **Le client fixe `espace_id`/`created_by`** (`store-mapping.js:59`, `store-supabase.js:99,159`) — **mais ce n'est pas une barrière et la base rejette la forge** :
  - INSERT → `WITH CHECK` exige `has_entite_write/has_role` sur l'`espace_id` **fourni** (`0010:98`) → écrire chez un autre tenant échoue sauf si on y est déjà rédacteur.
  - UPDATE (déplacer) → le trigger `freeze_espace_id()` lève `ESPACE_ID_IMMUTABLE` (`0009:19-30`) ; comme c'est un **trigger**, il bat **même le `service_role`** (le bypassrls saute les *policies*, pas les *triggers* — rationale explicite `0009:11-13`).
  - `ownerId` ne sert qu'au namespace de l'UUID déterministe (`det-uuid.js:52`) ; une collision → `ON CONFLICT (id) DO NOTHING RETURNING version` → `null` → `conflict`, fail-closed (`store-supabase.js:16-20,186-189`). Pas d'écrasement, pas d'effet cross-tenant.
- **Helpers d'autorisation** tous `SECURITY DEFINER` + `SET search_path=''` + `revoke public`/`grant authenticated` : `is_member`/`has_role` (`0002:6-41`), `is_full_member`/`is_full_manager` (`0029:123-161`), `has_entite_access`/`has_entite_write` (`0029:243-290`), `entite_of_*` (`0030:50-124`, `0042:33-64`). Un non-membre ne peut pas les faire renvoyer `true`.
- **Verrous d'immuabilité** : `prevent_locked_mutation` = trigger BEFORE UPDATE OR DELETE sur `baux` (`0015:38-40`) + `edl` (`0016:22-24`) → aucun membre (même owner/`service_role`) ne mute une ligne `locked`. *(Rappel : le seul angle mort est l'INSERT, cf. P0-1-bis.)*

### 🔵 RLS-GUC — Le bypass d'immuabilité repose sur un GUC de session, donc sur l'hypothèse « PostgREST ne peut pas faire `SET` »
**À confirmer en test réel.** Ancrages : `0014:25` (`current_setting('app.bypass_immutable', true)='on'`), `0023:20,52-53` (`app.bypass_owner_guard`).

Le trigger de verrou et `protect_last_owner` honorent un GUC transaction-local. La sûreté repose **entièrement** sur le fait que PostgREST n'expose aucun `SET`/option arbitraire au client. Rien dans les migrations lues ne l'expose → note de durcissement. **Test :** en tant qu'`authenticated` via PostgREST, tenter `select set_config('app.bypass_immutable','on',false)` puis `UPDATE` une ligne `baux` verrouillée → doit toujours lever `ROW_LOCKED_IMMUTABLE`.

## 3 · Partage SCI & invitations (surface 3)

### ✅ Modèle de partage : très bien bâti, pas de fuite cross-tenant — **prouvé par raisonnement**
- Un membre **scopé** est `full_espace=false`. `has_entite_access` (`0029:243-261`) n'est vrai que via `is_full_member` **ou** un grant `entite_membre` explicite `(espace, entite, user)` ; entité `NULL` → `false`. Un scopé lit **seulement** les SCI accordées, jamais « tout l'espace A ».
- **Escalade bloquée** : gérer `entite_membre` exige `is_full_manager` (`0029:301-319`) ; un scopé ne l'est jamais → il ne peut ni s'auto-accorder des SCI, ni écrire là où il ne fait que lire, ni changer les rôles. L'identité d'un grant est gelée (`0029:207-228`).
- **Invitations** (`0032`) : token `gen_random_uuid()::text` **unique, 122 bits** (`0032:24`) — non devinable, non énumérable ; `invitation_preview`/`accept_invitation` réservés à `authenticated`. Revoked/expired honorés côté serveur (`0032:122-125`). INSERT exige `is_full_manager AND created_by=auth.uid()` (`0032:96-97`). `accept_invitation` **fige** `role='lecture_seule', full_espace=false` (`0032:143-144`) et lit les grants **depuis la ligne** (jamais depuis l'invité) → **aucun chemin vers `role='owner'`**.

### 🟠 INV-1 — La ré-activation préserve `full_espace=true` (cas limite)
**À confirmer en test réel.** Ancrages : `0032:133-145`, `0003:44-47`.

`accept_invitation` fait `INSERT … ON CONFLICT (espace_id,user_id) DO UPDATE SET invite_status='active'` ; la garde `ALREADY_FULL_MEMBER` ne se déclenche que si la ligne existante est **à la fois** `active` **et** `full_espace=true`. Si un ex-membre **full** a été retiré par **désactivation** (flip de `invite_status`) plutôt que par `DELETE`, sa ligne garde `full_espace=true`. Accepter **n'importe quel** token ultérieur (même scopé) le **réactive en membre FULL** + ajoute les grants scopés.

**Scénario :** un ex-collègue retiré-par-désactivation regagne l'accès **full** à l'espace en acceptant une invitation SCI étroite. **Test :** désactiver un membre full (si c'est ainsi que l'app retire), puis lui faire accepter une invite scopée → vérifier si `full_espace` reste `true`. Si l'app utilise `DELETE` (policy `members_delete` existe), sans objet. **Correction :** la branche `ON CONFLICT` ne doit pas ressusciter `full_espace`.

### 🔵 INV-2 — Révoquer une invitation ne révoque pas l'accès déjà accordé (par conception). `status='revoked'` ne bloque que les futurs accepts ; les lignes `entite_membre`/`espace_members` persistent → prévoir un flux « retirer un membre » explicite.

### 🔵 Partage-INTRA — un gestionnaire scopé peut attacher un bail à un logement d'une autre SCI **du même espace** (`coalesce(entite_id, entite_of_logement(logement_id))` : le `with_check` n'évalue qu'`entite_id`). Intra-espace only, ne lit pas l'autre SCI. Moot tant qu'il n'y a pas de scopés.

### 🟠 RT-1 — Realtime : un membre scopé reçoit les événements de **toutes les SCI** de l'espace (OUVERT, devient 🔴 à l'activation du partage)
**Prouvé par raisonnement.** Ancrages : `0025:8-14`, warning `0030:34-41`, `0031:26-27`.

Les policies de `realtime.messages` filtrent sur `is_member(safe_uuid(split_part(realtime.topic(), ':', 2)))` — **niveau espace, pas par SCI**. Un membre scopé (qui *est* membre actif) peut s'abonner au canal `espace:<id>` et recevoir les **payloads de changement en direct de toutes les SCI** de l'espace, y compris celles qu'on ne lui a pas accordées. C'est la moitié non corrigée du trou que l'en-tête de `0030` signale explicitement. *(La moitié Storage, elle, a été corrigée par `0031` : re-scoping par entité `<espace>/<entite>/…` avec `has_entite_access/write`, bucket `espace-files` privé.)*

Borné aujourd'hui : payloads de sync (pas de binaires en masse), et **aucun membre scopé n'existe en prod** (partage non activé — règle `0030:39` « ⛔ ne pas créer de membre scopé en prod »). **À corriger avant d'activer le partage :** canal `espace:<id>:<entite>` + `has_entite_access` sur le 3ᵉ segment, ou filtrage serveur des payloads. **C'est l'item technique n°1 du partage.**

## 5 · XSS stocké & injection (surface 5) — *voir P0-2 ci-dessous, c'est ici que ça fait le plus mal*

### 🔴 P0-2 — XSS stocké cross-membre → vol de session (prise de contrôle en SCI partagée)

**Cause racine :** le code a **trois conventions concurrentes** pour « échapper une chaîne destinée à un `onclick` », et **une seule est correcte**.

| Motif | Lieu | Sûr dans une string JS ? | Sûr contre breakout d'attribut ? | Verdict |
|---|---|---|---|---|
| `escHtml(x)` seul | `index.html:4242`, `js/core/utils.js:16` | ❌ `'`→`&#39;` **re-décodé** en `'` dans un `on*` | ✅ | **CASSÉ en onclick** |
| `refSafe = x.replace(/'/g,"\\'")` | 15+ sites | ✅ | ❌ `"`/`<`/`>` non échappés | **CASSÉ (breakout `"`)** |
| `escHtml(x.replace(/\\/g,'\\\\').replace(/'/g,"\\'"))` = `_lyQ` | `index.html:28302` | ✅ | ✅ | **CORRECT** |

Le bon motif (`_lyQ`) JS-échappe **d'abord**, puis HTML-échappe. Tous les autres sites se trompent d'ordre ou sautent une moitié. L'auteur **savait** que la menace était le cross-membre — le commentaire `index.html:28300` dit « *saisie par un membre est rendue dans le DOM des autres* » — mais le correctif (`_lyQ`) n'a été appliqué **qu'à la liste Loyers**.

**Fait clé :** la session Supabase (access + refresh) est en `localStorage['immo-supabase-auth']` → toute exécution de script dans la page victime la lit et l'exfiltre → **prise de contrôle compte + tenant**.

#### 🔴 P0-2a — `escHtml`-seul dans `onclick` (breakout de string JS, au clic)
**Prouvé par raisonnement** (défaut d'échappement) · **à confirmer en test réel** (sync + clic). Le parseur HTML décode `&#39;`→`'` **avant** de compiler le handler inline en JS. ## 7 · Pages publiques & worker relais (surface 7) — *détaillé en A ci-dessus*

En plus de P0-1/P0-5/P0-6 (section A) :

### ✅ Modèle de token : prouvé sain
Tokens = HMAC-SHA256 sur JSON canonique (`tokens.js:25-30`) ; chaque garde lie `role` + id d'objet et **re-charge l'objet** (`requireSigner`/`requireOwner`/`requireCandidat`/`requireCandOwner`). ### 🔵 CORS-null — `'null'` dans l'allowlist CORS + wildcard localhost

## 9 · En-têtes & plateforme (surface 9)

### 🔴 P0-3 — Aucune CSP servie (la règle « tout vendored » est une convention, pas une barrière)
**Prouvé par raisonnement** (absence dans les sources) · **à confirmer en test réel** (en-têtes prod). Ancrage : `index.html:23817` (seul meta http-equiv présent = Content-Type) ; grep `Content-Security-Policy` → 0 occurrence ; pas de fichier `_headers` ; `.github/` ne contient que des workflows.

`index.html` n'a **aucune** `<meta http-equiv="Content-Security-Policy">`. L'app est servie par **GitHub Pages**, qui **ne peut pas émettre d'en-têtes de réponse custom** (pas de `_headers`). Donc la CSP ne pourrait venir que d'un meta — et il n'y en a pas. Conséquence : **aucune restriction `script-src`/`connect-src`/`frame-ancestors`**. La règle mémoire « aucun CDN externe au runtime » n'est tenue que par le vendoring + le passthrough du SW, **pas** par une CSP. Sur une app qui tient IBAN/PII/baux signés, **l'absence de CSP transforme le moindre XSS (P0-2) en exfiltration vers un serveur arbitraire**. C'est l'**amplificateur** de P0-2.

**Correction :** ajouter une CSP stricte en `<meta>` (`default-src 'self'; connect-src 'self' https://<projet>.supabase.co https://<relais> ; script-src 'self'` — noter qu'il faudra sortir les handlers inline `onclick`, ce qui rejoint la correction de fond de P0-2). Envisager un hébergement qui sait poser des en-têtes (Cloudflare Pages) pour une vraie CSP + HSTS + `X-Frame-Options`.

### 🟠 F9.2 — Pas de protection anti-clickjacking
**Prouvé par raisonnement** · **à confirmer en test réel.** GitHub Pages ne pose pas `X-Frame-Options`, et `frame-ancestors` est **ignoré s'il est livré en `<meta>`** (spec). L'app peut être mise en iframe par n'importe quel site → clickjacking sur l'UI authentifiée (piéger un clic sur « Restituer le dépôt », « Signer », une confirmation de purge). **Seule parade sur GH Pages :** un frame-buster JS dans `index.html` (`if (self !== top) top.location = self.location`).

### 🔵 F9.3 — CSRF non applicable (mitigation) ; HSTS effectif
Supabase et le relais s'authentifient par **bearer tokens dans l'en-tête `Authorization`** (`supabase-entry.js:195`, relais `index.js:32`), **pas par cookies** → le navigateur n'attache pas d'en-tête cross-site → **CSRF classique n.a.** (aucune action requise). HSTS : `*.github.io` est dans la **liste de preload HSTS** → HTTPS forcé pour l'origine prod même sans en-tête explicite.

**Realtime isolé :** cf. RT-1 (surface 3). CSP/headers : cf. P0-3.

## 19 · Audit-log & RGPD (surface 19)

### 🔴 P0-4 — Le journal d'audit est réécrivable : l'utilisateur audité peut effacer ses traces
**Prouvé par raisonnement.** Ancrages : `js/core/audit-trail.js:12-13,27-35`, `js/core/store-sync.js:23,129`, absence de table d'audit dans `supabase/migrations/`.

`DB.auditTrail` est un simple tableau côté client (`audit-trail.js:12-13`), persisté **à l'intérieur du blob `config` unique** que le client réécrit **en entier** à chaque sauvegarde (`store-sync.js:23,129` : « config (params/…/auditTrail/…) → un seul blob »). **Il n'existe aucune table d'audit côté serveur** (les migrations qui mentionnent « audit » n'en créent aucune — seulement des commentaires). Le module le confirme : « Pas de purge automatique… L'utilisateur peut purger manuellement via UI Paramètres » (`audit-trail.js:27-30`).

**Conséquence :** comme tout le `auditTrail` part dans un blob rédigé par le client, **n'importe quel utilisateur** (y compris un membre malveillant) peut envoyer une sauvegarde de config avec des entrées **supprimées ou modifiées** — effaçant ses traces — et la RLS **ne peut pas distinguer** une mise à jour de config légitime d'une falsification d'audit (même blob, même ligne, même droit d'écriture). Pour un journal dont le but affiché est le **registre RGPD art.30** et la **traçabilité CRG mandataire** (`audit-trail.js:6-11`), c'est un échec d'intégrité/non-répudiation. 🔴 pour la conformité, surtout en **SCI partagée** où les actions d'un membre sont précisément l'objet de l'audit.

**Correction :** déplacer les événements d'audit vers une **table Supabase dédiée append-only**, avec une RLS **`INSERT`-only** (aucun droit `UPDATE`/`DELETE`), `ts`/`user_id` **tamponnés serveur**.

### 🔵→🟠 F19.2 — `userId` de l'audit est une chaîne **générée côté client**, spoofable
**Prouvé par raisonnement.** Ancrage : `audit-trail.js:87-100`. `_getCurrentUserId()` lit `window.DB.params.userId` (génère un `usr_…` aléatoire si absent) — **ce n'est pas** le `user.id` Supabase authentifié. Le « qui » de chaque entrée est donc auto-déclaré, trivialement falsifiable, non lié à l'identité auth. Aggrave P0-4.

### ✅ Droit à l'effacement — serveur-enforced (bon design)
`js/core/espace-purge.js:1-11` est UX-only ; la vraie garde est la RPC `purge_mon_espace` (`0041`, `SECURITY DEFINER`, owner + nom exact re-vérifiés), invoquée à `supabase-entry.js:1327`. **Caveat à confirmer live :** la purge doit **aussi** supprimer les objets **Storage** Supabase **et** le résidu IndexedDB (cf. F14.1) — confirmer que `purge_mon_espace` cascade vers le Storage, pas seulement les lignes DB.
