## 2. Tokens

- Format (tokens.js:25-30) : `base64url(JSON payload).base64url(HMAC-SHA256(payload))`, clé = `env.SIGNING_SECRET` (importée en UTF-8 brut ; aucune vérification de longueur minimale). Pas de JWT standard, pas de champ `alg`/`kid`, pas de rotation de clé.
- Payloads : signer `{sid, role:'signer', idx, jti, exp}` ; owner `{sid, role:'owner', ep, jti, exp}` ; cand-owner `{lid, role:'cand-owner', jti, exp}` ; candidat `{lid, role:'candidat', jti, exp}`.
- Aléa : `jti = randomHex(8)` (64 bits, `crypto.getRandomValues`, crypto-utils.js:57) ; `sessionId` / `linkId` = `randomHex(32)` = 256 bits CSPRNG (sessions.js:145, candidatures.js:139) ; `pieceId` = `randomHex(8)` (64 bits). `jti` n'est ni stocké ni vérifié (aucune liste de jetons).
- Stockage : aucun token stocké en KV (stateless). Les identifiants de session (`sessionId`, `linkId`) sont des clés KV en clair (`session:{sid}`, `cand:{lid}`). Les emails sont stockés hachés (sha256 sans sel, `emailHash` : trim+lowercase) ; OTP stocké haché.
- Expiration : signer et owner `exp = now + 14 j` (`expEpoch`, index.js:39) ; candidat `exp = expiresAt` de la candidature (index.js:470) ; cand-owner `exp = now + expDays + 7 j` (index.js:444). `verifyToken` (tokens.js:44) rejette si `exp` numérique dépassé (un token sans `exp` serait accepté : le champ n'est pas obligatoire).
- Comparaison : `crypto.subtle.verify('HMAC')` (comparaison de la plateforme) ; hash email/OTP via `timingSafeEqualStr` (XOR sur octets ; retour anticipé si longueurs différentes).
- Révocation : owner de session uniquement, via epoch KV `epoch:{sid}` (`ep` du token < epoch courant → 401 `token-revoked`), bump par `reclaim` ; pas d'epoch pour signer, candidat, cand-owner (révocation candidature = statut `revoked`, tous tokens candidat refusés ; cand-owner reste valide).
- Usage unique : non. Signer token réutilisable tant que `idx === currentIndex` et statut ≠ completed ; GET `/s/:id` en refrappe à volonté ; owner token réutilisable jusqu'à exp/révocation. Token liée au rôle via `payload.role` et à la ressource via `sid`/`lid` (testé : tokens croisés → 401).
- sessions.js : pas de fonction de token ; porte `createSession`, `recordEmailVerified`, `recordOtp*`, `recordSignature`, `recordReclaim`. `createdBy` (= `sub` Supabase) sert de preuve de propriété durable pour `reclaim`.

## 3. OTP (otp.js, index.js:180-223, email-sender.js)

- Code 6 chiffres (`CODE_LEN=6`), `crypto.getRandomValues` Uint32 avec rejection sampling (uniforme).
- Stockage : `sha256("{sessionId}:{code}")` sans sel secret, dans `signer.otp.hash` ; mis à `null` après succès (non rejouable).
- Expiration 10 min (`OTP_TTL_MS`), `OTP_MAX_ATTEMPTS = 5` par code ; échec → `attempts++`, `expired-or-locked` (400) une fois verrouillé.
- Renvoi : chaque `verify-email` avec email correct génère un nouveau code et remet `attempts` à 0 (recordOtpSent, sessions.js:213) ; aucune limite sur le nombre de renvois ni délai entre deux envois (pas de rate-limit, cf. §8).
- Pré-requis : un `verify-email` ne renvoie un code que si l'appelant fournit l'email dont le hash correspond. En mode resend l'email part vers l'adresse saisie (qui a le même hash).
- `EMAIL_MODE` (wrangler.toml:25, valeur actuelle `"dev"`) : tout mode ≠ `'resend'` (y compris valeur absente/typo) = dev. En dev : `makeSender.send` renvoie `{sent:false, devCode: code}` (email-sender.js:9-12) ; la réponse HTTP de `verify-email` contient `devCode` (index.js:204) à **l'appelant détenant un signToken valide et connaissant l'email du signataire** ; la page l'affiche (`public/sign.js:150-152`, "Mode test"). Le code est aussi écrit dans les logs Worker (`console.log` avec email, bailRef, code — email-sender.js:10). `delivery = 'ecran-test'` est consigné et affiché dans les données owner (`otpDelivery`).
- `OTP_REQUIRED` (wrangler.toml:30, valeur `"false"`) : n'est évalué qu'à `/signed` (index.js:249) ; `=== 'true'` exige `otpVerifiedAt`, sinon 403 `otp-required`. À `false` (état actuel), la signature est acceptée sans email ni OTP vérifiés côté serveur (l'UI seule les impose). Le test de cette garde est explicitement absent (otp-routes.test.js:81).
- Resend : fetch `https://api.resend.com/emails` avec `Authorization: Bearer env.RESEND_API_KEY` ; échec → 502 `send-failed` (code resté en KV).

## 6. Signature / preuve

- Tamponnage serveur (sign-stamp.js:383) : le client n'envoie que l'image PNG de signature + paraphes ; le worker charge l'original KV (`getOriginalPdf`), lit le manifeste d'ancres embarqué (`readFromDoc`), dérive `sigId`, `side`, nom (nom du bail prioritaire), date serveur, et tamponne via `public/sign/stamp.js` (pdf-lib). Le client ne fournit jamais les octets du document.
- Chaînage : après chaque signature, `signed/{sid}.pdf` ET `original/{sid}.pdf` sont écrasés par le PDF signé (sessions.js:304-305) ; signataire N+1 tamponne par-dessus.
- Preuve par signataire (`signer.proof`, sessions.js:284) : `ip` (`CF-Connecting-IP`), `userAgent`, `signedAt` (serveur), `pdfSha256` (sha256 du PDF signé cumulé), `emailVerifiedAt`/`otpVerifiedAt` (autorité serveur), `signerName`/`nameSource`, et champs fournis par le client (`consentElectronic`, `luApprouve`, `openedAt`, `readCompletedAt`, `annexesRecuesAt`, `parapheTimes`) assainis et bornés. Aucun hash du PDF d'origine n'est calculé à la création ; aucun chaînage de hash entre signataires ; pas de signature cryptographique du PDF (pas de PAdES) ni d'horodatage tiers (TSA) dans le code lu.
- Stockage : tout dans KV (`session:{sid}` méta et preuves, `signed/`, `original/`), TTL 14 j renouvelé à chaque écriture ; suppression totale par `DELETE` owner ; aucune copie hors KV.
- Lecture : preuve via GET owner (route 9) ; PDF signé via GET owner (route 8). Écriture/écrasement : seul le chemin `/signed` (signer courant) écrase les PDF ; `POST /sessions` ne peut pas recréer un sid existant (sid aléatoire côté serveur) ; l'owner peut `DELETE`. `reclaim` journalisé dans `reclaims:{sid}` (clé séparée de la méta).
- Anti re-signature : `requireSigner` exige `idx === currentIndex` et statut ≠ completed (403/410) ; `recordSignature` lève si completed. Garde-fous absents du code : verrou atomique (KV sans CAS), comparaison `idx` du token vs `currentIndex` relu dans `recordSignature`. Anti-substitution de document : garanti par le tamponnage depuis l'original serveur (P0-1), testé (sign-e2e/routes).
- Candidatures : `cand:{lid}` (dossier JSON, méta pièces) + `cand-piece/{lid}/{pid}` ; lecture/écriture par candidat tant que `status === 'open'`, lecture par cand-owner ; pas de preuve/horodatage au-delà de `openedAt`, `submittedAt`.
